S/4HANA Monitoring MCP Server

PythonMCPRFCODataS/4HANA 2023

Problem

SAP Solution Manager and the standard Basis transactions (ST03N, ST06, SM50, ST22) expose a large amount of runtime data, but only to a human sitting at the SAP GUI. An AI agent asked to triage a performance regression has no way to read work-process state, dialog response times or short dumps without someone copying screens into the conversation.

The goal was a narrow, read-only bridge: expose the monitoring surface a Basis administrator actually consults, in a form an agent can query, without opening a write path into a production system.

Approach

The server implements the Model Context Protocol and exposes each monitoring domain as a tool with a typed schema: work-process overview, dialog and background response-time statistics, ABAP short dumps, tablespace growth and transport queue state. Every tool maps onto an existing SAP interface, RFC-enabled function modules where they exist and OData services from the S/4HANA monitoring APIs where they do not, and returns compact JSON rather than the raw screen layout.

A thin caching layer keeps polling load on the target system below what a single administrator refreshing SM66 would generate. Tool descriptions are written for the model, not for documentation: each states what question it answers and which parameters narrow the result.

tools:
  - get_workprocess_overview   # SM50 / SM66
  - get_response_time_stats    # ST03N, dialog + background
  - list_short_dumps           # ST22, last 24h by default
  - get_tablespace_growth      # DB02
  - get_transport_queue        # STMS

Architecture

full-width architecture diagram

Three layers: the MCP transport (stdio or HTTP), a domain layer that turns tool calls into normalised queries, and an adapter layer with one module per SAP interface. Credentials never reach the model. The adapter holds a technical user with display-only authorisations, and every call is logged with tool name and parameters for audit.

Key decisions and tradeoffs

Read-only by construction. No tool can start a transaction or change a parameter. The agent can diagnose but not remediate, which is the intended boundary for a first deployment.

Summarise in the adapter, not the prompt. Fixed schemas and pre-aggregated results cost fewer tokens and behave predictably. Rarely needed columns are dropped and must be requested through a separate detail tool.

Per-tool rate limits tuned to ST03N averages. Limits are set from the observed load of a human administrator, so the server can never be the heaviest dialog user on the system.

Outcome

Deployed against a development S/4HANA landscape. Triage that took 20–30 minutes of GUI navigation completes in a single agent turn with the relevant statistics attached. The code is proprietary; this writeup covers the architecture and the decisions, not the implementation.
