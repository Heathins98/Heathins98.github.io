Steam Achievement RAG

Answers "how do I get this achievement?" for Halo: The Master Chief Collection, grounding generated answers in Steam Community Guides.

Problem

Steam's achievement metadata is minimal — a name, a short description, a hidden flag — with nothing on how to actually earn one. Halo: The Master Chief Collection has around 700 achievements spread across its sub-games, and the real how-to knowledge for the obscure ones lives scattered across long-form Steam Community Guides, not in any structured field Steam exposes.

The question was whether a system could answer a specific achievement question accurately from that guide text — and, just as importantly, recognize when the guides don't cover an achievement and say so, rather than confidently inventing steps.

Approach

The system follows a "resolve, don't retrieve" philosophy: most questions name a specific achievement, so a cheap exact/fuzzy match against the ~700 known achievement names is tried first, before paying for anything more expensive. Only questions that don't resolve fall through to hybrid semantic search. The pipeline is five independently re-runnable stages, from raw API capture through to a scored evaluation run.

ingest/

Pulls raw achievement and guide data from the Steam Web API to JSON, intentionally unparsed.

  • Achievement list via ingest/achievements.py
  • Community Guides via ingest/guides.py
transform/

Parses, cleans, chunks and links the raw captures.

  • Sub-game parsing and language filtering
  • Structure-aware chunking and achievement linking
index/

Defines the schema and turns chunk text into searchable data.

  • schema.sql for the four core tables
  • MiniLM embedding and full-text indexing
retrieve/

The resolver, hybrid search and generation pipeline an end user's question actually runs through.

  • Exact/fuzzy resolver against known achievements
  • Hybrid search + cited Claude generation
eval/

Re-runnable scoring against a fixed gold set of questions.

  • 100 hand-written gold questions
  • eval/metrics.py for accuracy breakdowns

Architecture

A question first hits the resolver, which checks it against the ~700 known achievement names — exact match first, then fuzzy match. A resolved match pulls its pre-linked guide chunks directly, skipping search entirely. An unresolved question goes to hybrid search: dense vector similarity (384-dimensional MiniLM embeddings in pgvector) and PostgreSQL full-text keyword ranking run in parallel and are combined with Reciprocal Rank Fusion, since cosine similarity and BM25 scores aren't on a comparable scale. Either path lands on the same generation step, where Claude produces a cited answer from the retrieved chunks or explicitly declines when nothing relevant was found.

All of it sits on four tables in a single PostgreSQL 17 + pgvector database: achievements (~700 rows with name, description, hidden status, sub-game), guides (Community Guide metadata), chunks (guide text split at section boundaries, carrying both the embedding and the full-text vector), and achievement_chunks (the bootstrap links between achievements and the chunks that explain them).

Key decisions and tradeoffs

Resolve before retrieving.

Most questions name a specific achievement rather than describing one vaguely. Trying exact/fuzzy matching against the known achievement list first, before any embedding or search, costs almost nothing and hits 98% accuracy on exact-name questions — reserving the expensive hybrid search path for the minority of questions that actually need it.

Reciprocal Rank Fusion, not a blended score.

Dense cosine similarity and PostgreSQL's BM25-style full-text ranking sit on incompatible scales, so averaging or weighting the raw scores lets whichever one happens to have larger magnitude dominate. Fusing by rank instead keeps both signals meaningful without hand-tuning a weight.

One PostgreSQL database, not a separate vector store.

Structured achievement metadata, full-text indexes and pgvector embeddings all live in the same PostgreSQL 17 instance rather than splitting vectors into a dedicated vector database. That avoids keeping two stores in sync and lets a single query join structured filters with vector search.

Structure-aware chunking, two-pass linking.

Guides are chunked at their real section boundaries — further subdividing sections that cover multiple achievements — rather than fixed-size windows, which preserves the retrieval signal a section boundary carries. Achievement-to-chunk links are then bootstrapped in two passes: exact name match first, then description match for achievements with flavor-text names that don't literally appear in guide text.

Generation must cite and may decline.

The generation step is required to ground its answer in the retrieved chunks with citations, and is explicitly permitted to say a guide doesn't cover the achievement rather than filling the gap with a plausible-sounding guess.

Outcome

Measured against a 100-question gold set, the resolver alone reaches 45% overall accuracy — 98% on exact achievement names, but only 3% on rephrased questions and 0% on vague descriptions, since it has no way to handle anything that isn't a near-literal name match. Adding hybrid search brings overall accuracy to 90%: 100% on exact names, 82% on rephrased questions, 81% on vague descriptions. That gap is the measurable case for hybrid search — it earns its cost specifically on the questions the resolver can't handle, while the resolver keeps the common case cheap and accurate.
