S/4HANA Monitoring MCP Server

Live SAP performance data, exposed to AI agents over the Model Context Protocol.

Problem

The standard Basis transactions (ST03/ST03N, SM50, SM66, /SDF/SMON) expose work-process load, memory pressure, dialog response times and queue depth, but only to a human sitting at the SAP GUI — and only one screen at a time. An AI agent asked to triage a performance regression has no way to read that state without someone copying screens into the conversation, and there's no standard REST or OData layer to fall back on: this data lives behind SAP's RFC protocol.

The goal was a narrow, read-only bridge: expose the same monitoring surface a Basis administrator already consults, in a form an MCP-compatible agent can query directly — including SAP's own Joule assistant, which can register external MCP servers as custom connectors.

Approach

The server is built on FastMCP 2.0 (Python 3.12) and exposes four tools, each a thin wrapper over a real RFC function module rather than a REST abstraction. pyrfc wraps SAP's native NW RFC SDK C library directly — there's no REST API, OData service or middleware translating in between. Every tool call is a raw RFC invocation, the same kind SAP GUI itself issues.

get_system_infoRFC_SYSTEM_INFO

Establishes system identity before any monitoring call runs — the first tool any agent calls to know which system it's talking to.

  • System ID, hostname, instance number
  • SAP release and ABAP kernel version
get_workload_statisticsSWNC_COLLECTOR_GET_AGGREGATES

The same aggregation transaction ST03 uses — step counts, response times and DB load by task type.

  • Steps, response time and CPU time by task type
  • Filterable by task type and server name
get_smon_snapshotsRFC_READ_TABLE

Reads /SDF/SMON_HEADER for up to ~17 hours of system health history at 30-second granularity.

  • CPU, memory and queue-depth time series
  • Time-range and instance filters
get_work_process_statusTH_WPINFO

Live work-process state across every application server instance in one call, not just the instance the connection landed on.

  • Process type, status, current user and program
  • CPU time elapsed and wait time

Architecture

Five layers sit between an AI client and the SAP kernel. AI clients — SAP Joule, Claude or another LLM, or any generic MCP client — talk to the FastMCP server over streamable HTTP on port 8000. The server calls into a thread-safe RFC connection pool of three connections with lazy initialisation; the pool talks to the SAP system over the RFC binary protocol on port 33xx, optionally through a SAPRouter proxy for multi-hop routes; that lands on the SAP S/4HANA application server, where the four function modules actually run.

Key decisions and tradeoffs

RFC over a REST/OData layer.

No REST or OData service in S/4HANA exposes work-process, SMON or short-dump data at the granularity ST03/SM50 show. Wrapping the RFC SDK directly via pyrfc means shipping a compiled SDK per platform (nwrfcsdk.dll / librfccm.so) instead of a lighter HTTP dependency, but it's the same protocol SAP GUI has used since the R/3 era — no missing data, no translation layer to maintain.

Fixed-width binary row parsing.

RFC_READ_TABLE returns /SDF/SMON_HEADER rows as fixed-width character strings with no structure of their own. The server reconstructs records from the FIELDS metadata table's byte offsets and lengths at read time — the same approach SAP's own ABAP programs use internally — rather than pushing that parsing onto the caller.

Connection pool with dead-connection recovery.

The server runs as a long-lived container, and SAP closes idle RFC sessions after a configurable timeout, which surfaces as RFC_CLOSED or a reset error on the next call. The pool detects a dead connection, discards it, opens a replacement and retries once, transparently to the caller, so a container running for weeks doesn't need manual intervention.

SAPRouter support via environment variables.

Production SAP systems are rarely reachable directly — enterprise landscapes route through SAPRouter, sometimes multiple hops. SAPRouter route strings are first-class configuration rather than a code path, so the same server handles direct, load-balanced and multi-hop-proxied connections without redeployment.

Outcome

Running against a real S/4HANA system rather than a sandbox, the server has cut triage that used to mean 20–30 minutes of GUI navigation down to a single agent turn with the relevant statistics attached. It's also registrable as a custom connector in SAP Joule Work Desktop, so SAP's own AI assistant can answer "is the system under load right now?" using live RFC data from inside the same system it's embedded in. The code is proprietary; this writeup covers the architecture and the decisions, not the implementation.
